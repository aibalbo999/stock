# 報告資訊密度閱讀預算設計

日期：2026-06-12

## 背景

目前報告中心的 HTML 報告會把多個高資料量區塊直向堆疊在同一條閱讀流中。這些區塊包含個股比較矩陣、個股建議、候選公司審計、自動補強任務、投資理由地圖、早期潛力雷達與展開細節。資料本身需要保留，因為既有測試與產品需求要求完整列數可追溯；真正的問題是每個區塊預設露出的卡片或列太多，讀者很快失去焦點。

本設計採用「閱讀預算」：每個長區塊先顯示少量高價值資料，告訴讀者還有多少內容可查，再把完整資料保留在同一區塊的展開區。這樣可以降低第一眼負擔，同時保留完整查核能力。

## 目標

- 讓報告讀者在每個長區塊先看到最重要的 3 筆資料。
- 所有長區塊使用一致節奏：摘要、優先 3 筆、剩餘數量提示、展開完整內容。
- 保留所有原始報告內容與完整 HTML 呈現，不移除資料、不改 Markdown 格式。
- 讓現有「完整資料必須存在」的測試可以改為驗證完整資料存在於展開區。
- 維持下載 HTML 與 Streamlit iframe 報告的同一份呈現邏輯。

## 非目標

- 不改報告產生器、評分規則、資料抓取、候選公司驗證或品質門檻。
- 不新增前端篩選器、搜尋器或多頁報告導航。
- 不改 Markdown 報告模板與既有章節標題。
- 不移除「完整文字」與「資料查核」分頁。

## 方案

採用「閱讀預算」方案。

每個長區塊分成三層：

1. 區塊標題與總量，例如「個股比較矩陣（20 檔）」。
2. 預設摘要區，最多顯示 3 筆高價值資料。
3. 完整資料展開區，使用 `<details>` 保留完整卡片或清單。

預設摘要不代表資料被篩掉；它只是閱讀入口。完整資料仍在同一份 HTML 中，並且可以被下載、查核與測試。

## 預設分層

固定露出：

- 報告品質狀態、配置額度、正式分析股票數與候選清單數。
- 重點摘要。
- 下一步行動中的處理原則與最高優先任務。

套用閱讀預算：

- 個股比較矩陣：顯示最重要 3 檔，其餘展開。
- 個股建議：顯示最重要 3 檔，其餘展開。
- 候選公司審計：顯示弱證據、待補資料或風險最高 3 張，其餘展開。
- 自動補強任務：顯示最高優先 3 項，其餘展開。
- 投資理由地圖：顯示最重要 3 張，其餘展開。
- 早期潛力雷達：顯示最重要 3 張，其餘展開。
- 下一步行動：處理原則固定露出，各類股票清單套用摘要與展開。

預設收合：

- 時間口徑。
- 判斷準則。
- 投資行動限制。
- 資料完整度。
- 來源覆蓋。
- 評分明細。
- 個別公司分析。

## 優先排序規則

各區塊的預設 3 筆應以「行動價值」排序，不只取原表前 3 列。

個股比較矩陣：

- 先顯示可小額分批研究。
- 再顯示高風險或避開項目。
- 最後顯示一般觀察項目。
- 同一類別內維持 Markdown 原順序，避免引入新的分數邏輯。

個股建議：

- 先顯示可研究或有配置建議的項目。
- 再顯示避開或降低曝險項目。
- 最後顯示一般觀察項目。

候選公司審計：

- 先顯示弱證據、待補資料、補查後未升格、資料不足排除。
- 再顯示正式分析項目。
- 同一狀態內維持原順序。

自動補強任務：

- 先顯示 `high` 優先級。
- 再顯示 `medium`。
- 最後顯示其他優先級。

投資理由地圖與早期潛力雷達：

- 若現有章節已有排序，維持原順序取前 3 筆。
- 不新增跨章節排序或模型判斷。

下一步行動：

- 「處理原則」固定露出。
- 每個行動群組最多顯示 3 筆。
- 群組內完整清單放在展開區。

## 介面呈現

每個閱讀預算區塊應有一致 affordance：

- 標題列顯示總數與預設顯示數，例如「顯示 3 / 20」。
- 摘要卡片下方顯示「另有 17 筆可展開」。
- 展開區標題使用明確文字，例如「展開全部 20 檔」或「查看完整候選審計」。
- 若總數小於等於 3，不顯示剩餘提示，也不需要額外展開區。
- 若沒有資料，保留既有空狀態文字。

視覺樣式維持目前報告的工作型介面風格：低裝飾、清楚分隔、8px 以下圓角、狀態色沿用現有綠色、琥珀色、紅色與藍色語意。

## 實作邊界

主要修改位置：

- `app/ui/report_html.py`
  - 增加共用閱讀預算 helper，負責組合摘要 HTML、剩餘提示與 `<details>` 完整區。
  - 將長區塊接到共用 helper。
- `app/ui/report_sections.py`
  - 讓長清單 renderer 支援回傳總數、摘要 HTML 與完整 HTML，或接受預覽數量。
  - 保留現有 HTML card 結構與 badge class。
- `app/ui/report_candidate_audit.py`
  - 若候選公司審計需要排序摘要卡片，新增最小 helper，不改審計資料模型。
- `app/ui/styles/report_html.css`
  - 新增閱讀預算提示列、展開區、摘要狀態文字的樣式。
- `tests/test_streamlit_report_html.py`
  - 補上閱讀預算行為測試。
  - 既有「完整列數」測試改成確認完整資料仍存在於展開區。

不修改位置：

- `app/templates/report.md.j2`
- `app/services/report_generator*.py`
- `app/services/report_markdown_sections.py`
- 資料抓取、評分、品質門檻與自動補強服務。

## 資料流

既有資料流維持不變：

1. 後端產生 Markdown 報告。
2. 報告中心讀取 `/reports/{report_id}`。
3. `report_html(markdown, history_result)` 解析 Markdown 章節。
4. 各區塊 renderer 產生 HTML 卡片或清單。
5. 閱讀預算 helper 將摘要與完整內容包成一致結構。
6. Streamlit iframe 與下載 HTML 使用同一份 HTML 字串。

## 錯誤與空狀態

- 若章節不存在，維持既有行為，不渲染該區塊或顯示既有空狀態。
- 若資料列數小於等於 3，直接渲染全部內容，不額外加 `<details>`。
- 若排序所需欄位缺失，退回原始 Markdown 順序。
- 若候選審計同時有 Markdown 與 result payload，以既有資料來源優先規則為準，不新增合併邏輯。

## 可及性

- `<details>` / `<summary>` 使用原生語意，保留鍵盤操作能力。
- Summary 文字需包含完整數量，例如「展開全部 20 檔」，避免只寫「更多」。
- 不用 hover-only 操作承載必要資訊。
- 狀態色仍搭配文字標籤，不只靠顏色辨識。

## 測試計畫

新增或調整以下測試：

- `test_report_html_collapses_large_comparison_matrix_to_reading_budget`
  - 驗證個股比較矩陣主畫面只顯示 3 張摘要卡片。
  - 驗證完整 20 檔仍存在於展開區。
  - 驗證「另有 17 檔可展開」提示存在。
- `test_report_html_collapses_candidate_audit_to_priority_preview`
  - 驗證候選審計優先顯示弱證據與待補資料。
  - 驗證正式分析與其他候選仍在完整展開區。
- `test_report_html_collapses_next_step_groups`
  - 驗證處理原則固定露出。
  - 驗證長群組預設 3 筆，其餘展開。
- `test_report_html_does_not_wrap_short_sections`
  - 驗證 3 筆以內的區塊不出現多餘展開提示。
- 更新既有完整列數測試，從「直接 count 主畫面卡片」改為「完整資料存在於展開區」。

## 驗收標準

- 報告首頁第一眼不再把每個長區塊完整展開堆疊。
- 每個長區塊都有一致的摘要與展開規則。
- 使用者能在不展開完整資料的情況下看完核心報告。
- 完整資料仍留在同一份 HTML 中，可下載、查核、測試。
- 不改變報告 Markdown、資料生成、評分或補強行為。
